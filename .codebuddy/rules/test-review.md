# 测试用例评审标准（QA Lead 视角）

> 本规则用于约束 AI 在「评审测试用例」类任务下的行为与输出格式。
> 触发场景：用户要求做"测试评审 / 覆盖矩阵 / 测试质量 review / 测试缺口分析"等。

## 一、评审目标（四方对账）

AI 应做的是**对账**而非"判定测试对错"，把人最容易漏的覆盖缺口与质量瑕疵挑出来。

四方对账：
1. **需求侧**：PRD 的 User Story / AC（验收条件）
2. **设计侧**：API 文档的端点、错误码、状态码
3. **实现侧**：业务代码的真实分支
4. **测试侧**：现有测试用例

任一侧出现没有被另外三侧呼应的内容，都是评审要标出来的点。

## 二、评审维度（按权重排序）

| 权重 | 维度 | 检查要点 |
|---|---|---|
| 1 | **需求覆盖完整性** | 每条 AC 是否有测试呼应；新增 AC 是否漏测 |
| 2 | **API 契约覆盖** | 每个端点的 200 / 4xx / 5xx 是否都有用例 |
| 3 | **边界值覆盖** | 0 / -1 / 最大值 / null / 空串 / 空集合 / 临界值（如 capacity=50 vs 51） |
| 4 | **负面用例覆盖** | 权限拒绝、并发冲突、状态非法、参数畸形 |
| 5 | **断言强度** | 只判 `not null` / 只判 `status == 200` 视为弱断言 |
| 6 | **测试独立性** | 无共享可变状态、无顺序依赖、可任意单跑 |
| 7 | **命名可读性** | 从方法名能看出「测什么 + 期望什么」 |
| 8 | **mock 与实现一致性** | mock 行为是否与真实实现的方法签名、返回值约束一致 |

## 三、严重度定义

| 严重度 | 标准 | 处置 |
|---|---|---|
| **High** | 缺失会导致生产事故（资金、权限、并发、安全相关 AC 未覆盖） | 必须补 |
| **Med** | 影响维护性，长期累积成债（断言弱、命名差、负面用例缺） | 建议补 |
| **Low** | 风格/可读性，团队可酌情 | 可选 |

## 四、AI 输出格式（强约束）

### 4.1 覆盖矩阵

必须用 markdown 表格，列固定如下：

```
| AC 编号 | AC 描述 | 关联测试 | 覆盖状态 | 缺口说明 |
|---|---|---|---|---|
| US-02 / AC-1 | 时长 ≥ 15 分钟 | BookingServiceImplTest#TimeValidation_短于15分钟拒绝 | ✅ | — |
| US-02 / AC-N | 不允许超过 NOW+7 天 | BookingServiceImplTest#TimeValidation_超过7天拒绝 | ✅ | — |
| US-05 / AC-3 | 上级取消必须填原因 ≥ 5 字 | — | ❌ | 缺 CancelService 测试，建议补 cancel_byManager_withShortReason_thenReject |
```

覆盖状态用：✅ 完全覆盖 / ⚠️ 部分覆盖（只测了 happy path）/ ❌ 未覆盖

矩阵末尾必须输出一行小结：
> 覆盖率小结：共 N 条 AC，✅ X 条，⚠️ Y 条，❌ Z 条；High 缺口 K 条。

### 4.2 行级 Review（针对单个测试文件）

```
| 行号 | 严重度 | 类型 | 问题 | 建议改法（1 句） |
|---|---|---|---|---|
| 45 | High | 断言弱 | 仅断言 result != null，未校验 status 字段 | 加 assertThat(result.getStatus()).isEqualTo(CONFIRMED) |
| 78 | Med | 命名差 | 方法名 testBook1 看不出意图 | 改为 book_whenRoomMaintenance_thenThrowRoomNotAvailable |
```

### 4.3 评审报告（汇总）

固定 5 段结构：

```markdown
# 测试评审报告 — {模块名} — {日期}

## 1. 执行摘要（3 行）
- 结论：…
- 主要风险：…
- 建议优先级：…

## 2. 覆盖矩阵
（4.1 的表）

## 3. 质量问题清单
（按 High → Med → Low 排序，每条带文件路径 + 行号）

## 4. 已补缺口
（本次评审顺手补的测试，列文件 + 用例名）

## 5. 剩余风险与下一步
- 仍未覆盖的 AC：…
- 建议引入的工具：JaCoCo / Testcontainers / Playwright …
```

## 五、AI 必须遵守的边界（不能做的事）

1. **不要决定"这个用例该删"** — AI 没有运行历史与失败率上下文
2. **不要给出覆盖率百分比数字** — 让 JaCoCo / vitest --coverage 出，AI 只解读趋势
3. **不要直接合入修改后的测试** — 修改建议作为 diff 提出，由人决定是否采纳
4. **不要"放宽"现有断言** — 弱断言要补强，绝不能因为测试失败就把 `equalTo` 改成 `notNull`
5. **不要凭空发明 AC** — 只能引用 PRD / requirement_review 中存在的条目；找不到对应 AC 时写「需求侧未明确」

## 六、推荐 Prompt 触发词

用户说以下任一关键词时，AI 应自动加载并遵循本规则：
- "测试评审 / 评审测试用例"
- "覆盖矩阵 / 需求-测试覆盖"
- "测试质量 review / 测试质量分析"
- "测试缺口 / 测试 gap"
