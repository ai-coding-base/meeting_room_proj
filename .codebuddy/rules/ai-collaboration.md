# AI 协作流程与话术库

> 本规则同时面向 **AI** 和 **开发者**：
> - AI：明确"修改类任务"的行为契约
> - 开发者：学会用结构化话术高效引导 AI

---

## 2. AI 在"修改/调优"任务中的强制行为

### 2.1 必须先做的事（编码前）

```
1. 复述理解：
   "我理解您要修改 XXX，达到 YYY 效果，对吗？"

2. 列出假设：
   "我会基于以下假设：
    - 假设 1：xxx
    - 假设 2：xxx
    如有不符请打断。"

3. 列出涉及范围：
   "本次修改预计触及：
    - 文件 A：修改方法 X
    - 文件 B：新增类 Y
    - 测试 C：补充用例
    其他文件不动。"

4. 等待开发者确认（小改可自行推进，大改 100+ 行必须等）
```

### 2.2 修改后必须输出

```
✅ 已完成修改：
- 改动 1：xxx（why）
- 改动 2：xxx（why）

❌ 未做（用户没要求）：
- xxx

📊 测试结果：
- 单测：X/Y 通过
- 失败原因：xxx（如有）
```

### 2.3 红线行为（AI 禁止做）

| ❌ 禁止 | ✅ 应当 |
|---|---|
| 顺手"美化"邻近代码 | 只动必须动的 |
| 自由删除"看似没用"的代码 | 提醒开发者，不擅自删 |
| 为了让测试通过而修改测试期望 | 修代码而不是修测试 |
| 添加未要求的错误处理 / 配置项 | 严格按需求 |
| 升级/替换依赖版本 | 先告知，等确认 |
| 发现需求矛盾装看不见 | 立即停下来提问 |

## 3. 开发者引导 AI 的高效话术

### 3.1 START 框架（启动新任务）

```
[S] Stage：当前在哪个阶段（需求/设计/编码/调优）
[T] Task：具体要做什么
[A] Asset：相关文档/代码位置
[R] Rule：要遵守哪些规则
[T] Test：成功标准是什么

示例：
"[阶段：编码] 实现 BookingService.create 方法。
 参考 docs/prd.md US-02 + docs/schema.md 第 2.1 节。
 遵守 .codebuddy/rules/java-backend.md。
 成功标准：单测覆盖 happy path + 时段冲突 + 幂等三种场景。"
```

### 3.2 修改类任务话术（FIX 框架）

```
[F] Fact：当前现象（实际看到什么）
[I] Intent：期望行为（应该是什么）
[X] eXample / eXtra：复现步骤 / 报错栈 / 边界条件

示例（差）：
❌ "这里有 bug，改一下"

示例（好）：
✅ "[FACT] BookingServiceTest#testCreate 失败，DuplicateKeyException 被吞了
    [INTENT] 应该转为 BookingConflictException 抛给 Controller
    [EXAMPLE] 报错栈：xxx；触发场景：两个并发请求订同一时段"
```

### 3.3 调优类任务话术

```
"[现象] 接口 P95 延迟从 200ms 涨到 800ms
 [范围] 仅影响 GET /api/rooms/{id}/availability
 [假设] 怀疑 N+1 查询
 [边界] 不要改业务逻辑，仅做查询优化
 [验证] 优化后压测 100 QPS P95 < 300ms"
```

## 4. 反例对照表（开发者常见低效话术 → 改进版）

| ❌ 低效 | ✅ 改进 |
|---|---|
| "不对，再改一下" | "[FACT] 输出的 status 是 CONFIRMED，[INTENT] 应该是 PENDING（VIP 走审批），[ASSET] 见 prd.md US-04" |
| "这个太复杂了" | "我希望简化为 X 步：1...2...3...，不要 Y 抽象" |
| "加点错误处理" | "对 X 异常，应返回 409 + code=BOOKING_CONFLICT；对 Y 异常，记录日志后透传" |
| "性能优化一下" | "QPS 目标 100，P95 < 300ms，可用 Redis 缓存 1 分钟" |
| "测试也写一下" | "用 JUnit 5 + Mockito，覆盖 happy path + 冲突 + 幂等三场景，禁用 Testcontainers" |
| "重构这个文件" | "拆出 X 方法到独立类 Y，Z 不动；保持现有公共 API 签名不变" |

## 5. AI 失控时的"刹车话术"

当 AI 开始自由发挥时，立即用以下话术拉回：

```
🛑 "停。请回滚未确认的修改，只保留 [具体范围] 的改动。"

🛑 "你刚才动了 X，但我没要求。请说明理由，否则撤销。"

🛑 "在你继续之前，先回答：
     1. 这次修改触及哪些文件？
     2. 每个改动对应哪条需求？
     3. 是否引入了新依赖？"

🛑 "不要假设。给我列出 3 种可能的解读，我来选。"
```

## 6. AI 自检：每次响应前问自己

- [ ] 我的修改范围是否仅限于用户的直接请求？
- [ ] 我有没有做"顺手"的改动？
- [ ] 我有没有添加未要求的功能 / 配置？
- [ ] 我有没有改了用户没说要改的代码风格？
- [ ] 我引入了新依赖 / 升级了版本吗？
- [ ] 修改后能否回答："每行变更追溯到哪条需求？"

任何一项答不出，立即**回退并提问**。

## 7. 阶段切换的明确信号

开发者用以下"明确信号词"切换阶段，AI 必须识别并加载对应规则：

| 信号词 | 切换到 | 加载规则 |
|---|---|---|
| `审视需求` / `review` | 阶段 1 | requirement-review.md |
| `生成 PRD` / `设计 schema` / `技术方案` | 阶段 2 | design-doc-template.md |
| `实现` / `开发` / `写代码` | 阶段 3 | java-backend.md / react-frontend.md |
| `修改` / `调整` / `不对` / `优化` | 阶段 4 | 本文件 |

**未识别明确信号时**，AI 应主动询问："当前是哪个阶段？"

## 8. 协作好坏的可观测信号

### 协作好（rules 生效）的信号

- ✅ 每次提交都能找到对应的 PRD User Story 编号
- ✅ AI 主动提风险，而不是闷头写
- ✅ 修改类任务很少返工
- ✅ 输出风格在团队内强一致

### 协作差（rules 失灵）的信号

- ❌ 反复"不对再改"
- ❌ AI 输出与项目风格不一致
- ❌ 大改动 AI 不打招呼直接做
- ❌ 团队成员各用各的 AI 流程

发现差信号时，**反思 rules 是否需要补充**，而不是放弃 rules。
